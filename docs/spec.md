# ddviz 仕様

列をドラッグ＆ドロップしてグラフを組み立てる可視化アプリ。オフラインで動くスタンドアローン exe として提供する。

## 要件

| 項目 | 内容 |
| --- | --- |
| 実行形態 | exe 単体。オフライン環境で動作する |
| 対象 OS | Windows 11、Windows Server 2016 |
| メモリ | 16GB RAM の PC で問題なく動くこと |
| 入力 | Parquet ファイル、または Parquet を格納したフォルダを指定して Load する |
| データ置き場 | ローカル SSD。ネットワークドライブは想定しない |
| グラフ種別 | 散布図、箱ひげ図（他種別は後回し） |
| フィルタ | 読み込んだデータのローカルフィルタ |
| D&D で指定する役割 | x/y 軸、facet（col, row）、第 n x/y 軸、overlay（≒symbol）、color |
| 散布図の平滑線 | csaps、GCV 平滑化スプライン、lowess から選択（必須） |

## データの性質

- 規模：1 億行 × 10 万列、facet は 10 × 10 程度。
- 10 万列はかなり疎（大半が null）。
- 列の型は数値中心で、カテゴリが混在する。
- 1 つのグラフで使うのは数列だけ。全列を描画に使う用途はない。
- 全量ロードはしない。グラフに必要な列だけを読む。
- Parquet は ddviz の外で作られ、渡されたものを読む。行グループのサイズやファイルの分け方は ddviz 側で選べない前提で設計する。
- 必要なら、読み込み時に ddviz が裏で変換やキャッシュ作成（フッタの索引化、列方向の分割など）をしてもよい。ただし、ユーザーに追加の作業（変換コマンドの実行、設定、待ち時間の明示的な操作など）をさせる UX は不可。変換は Load の中で自動で行う。

## 技術スタック（未決定）

UI の候補は次の 3 案。計測結果を見て決める。

| 案 | 使う言語 | 長所 | 短所 |
| --- | --- | --- | --- |
| FastAPI + htmx + 少量 JS | 周辺 UI（ファイル選択、列リスト、フィルタパネル）は htmx、D&D と描画は JS（SortableJS など）、データ処理は Python | ビルド工程なし。グラフ仕様をサーバー側で保持でき、フロントの状態管理がほぼ不要 | htmx 単体では D&D と描画はできない。描画まわりの JS が増えると htmx との二重管理が窮屈になる。Server 2016 では WebView2 の扱いが SPA 案と同じく要る |
| Svelte・Vue の SPA + Python サーバー | 画面は JS（Svelte か Vue）、データ処理は Python | 状態管理がきれい | Node のビルドが増える（実行時は不要）。Server 2016 では WebView2 が無いため、固定版ランタイムの同梱かブラウザ起動が要る |
| PySide6 + pyqtgraph | すべて Python（QtWebEngine を使わない限り JS なし） | ネイティブ窓で WebView2 が不要 | この規模では点を直接描けないため、高速描画の利点が効きにくい |

JS を書かずに済むこと自体は選定基準にしない。Python と JS は適材適所で使い分ける。

最初の検討での評価：

- 当初の推奨は「htmx 案で始め、JS が膨らんだら SPA 案へ移る」。
- 1 億行 × 10 万列の規模では、フロントは集約済み画像と軸を表示するだけになるため、htmx 案はむしろ成立しやすい。
- PySide6 案の売りだった大量点の高速描画はこの規模では効かず、優位はほぼ消える。

どの案でも、点をフロントへ送ることはできない。集約はすべてサーバー（Python）側で行い、フロントは集約済み画像と軸を表示する。

### 方針案（未確定）

- Load：スキーマだけ読み、列はオンデマンドで射影読込する。
- 散布図：サーバー側でビン集約して画像化する（bin_x × bin_y × color の group_by でカウント）。ズーム時は再ラスタライズする。
- 平滑化：x をビン集約（重み＝件数）してから適合する。
- exe 化：PyInstaller。

### プロセス構成（未決定）

Parquet の読込と集約は、UI とは別のプロセスで行う（2026-10-26 決定）。理由：フッタ解析や読込で使ったメモリを、プロセスは OS に返さない（「計測結果」）。UI のプロセスは集約結果だけを受け取り、小さいまま保つ。

要件：操作していない間にデータ用プロセスがメモリを占有し続けることは許容しない（2026-10-26 ユーザー判断）。常駐ワーカーが LazyFrame を保持すると、100 万チャンクで約 0.9GB、1000 万チャンクで約 9GB を掴み続ける見込みで、これは不可。

前提となるトレードオフ：フッタを解析済みのまま保持すればメモリを占有し、保持しなければ読込のたびに解析時間がかかる。待機プロセスを先に立てておく工夫ではこの関係は変わらない。両方を減らすには、1 回の読込で解析するフッタそのものを小さくするしかない。

候補：

| 案 | 内容 | 占有し続けるメモリ | 1 回の読込の待ち時間 | 課題 |
| --- | --- | --- | --- | --- |
| 1. 列分割キャッシュ + 使い捨てプロセス | Load 時に裏で、元ファイルを列方向に分割したキャッシュ（例：1000 列ずつ）を作る。import 済み（フッタ未解析）の待機プロセスを先に立て、読込のたびに必要な列のファイルのフッタだけを解析し、終わったらプロセスごと捨てる | 待機プロセスの約 50MB | 分割後のフッタ解析のみ（例：1000 万チャンクのファイルを 1/100 に分割すると、約 90MB・約 0.05 秒の見込み） | 初回 Load の変換時間と、元データと同程度のディスク使用量。未計測 |
| 2. アイドル終了する常駐ワーカー | 操作中は常駐して LazyFrame を使い回し、一定時間操作がなければ終了してメモリを返す | 操作していない間はゼロ。操作中は案 3 と同じ | 2 回目以降は約 0.04 秒。アイドル後の最初の 1 回は、起動・import・フッタ解析の分だけ待つ | 操作中の占有量は減らない。アイドル判定の時間は未定 |
| 3. 解析済み待機プロセス + 使い捨て | import とフッタ解析まで済ませた待機プロセスを先に立てておき、1 回使ったら捨てて次を立てる | 待機プロセスがフッタ分（常駐ワーカーと同じ）を占有する | 待ちはほぼ隠せる | 占有量は常駐ワーカーと変わらない。入れ替えの間は 2 プロセス分が同時に乗る |
| 4. 常駐ワーカー | 1 つのワーカーが常駐し、ファイルごとに LazyFrame を保持する | フッタ分 + これまでで最大の読込・集約のピーク | 2 回目以降は約 0.04 秒 | 要件を満たさない |
| 5. 素の使い捨てプロセス | 読込のたびにプロセスを起動して終了する | ほぼゼロ | 毎回、起動・import 約 0.7 秒とフッタ解析（100 万チャンクで約 0.5 秒、1000 万チャンクで約 5 秒） | 操作のたびに 1〜6 秒待ち、D&D での試行に合わない |

- 現時点の第一候補は案 1。変換コストが重すぎれば案 2 にする。
- どの案でも、読込中のピークメモリは減らない。1 億行の射影読込と集約のピークは未計測。
- polars の import 時間は、`uv run` の開発環境で 5 回計測し、いずれも約 0.72 秒だった（何もしないプロセスの起動は約 0.055 秒）。exe 化した後の値は未計測。

平滑化ライブラリ候補：

- GCV：`scipy.interpolate.make_smoothing_spline`（`lam=None`）
- csaps：`csaps` パッケージ
- lowess：`statsmodels` または自前実装

## 技術リスク

ボトルネックは「Parquet フッタ読込 → 列射影 I/O → ビン集約」の 3 点。UI の選択より先にここを計測する。

| リスク | 内容 | 対策案 | 確度 |
| --- | --- | --- | --- |
| 超ワイド Parquet のフッタ | フッタには「列 × 行グループ」ごとのメタデータが入り、読込時間とメモリは列チャンク数にほぼ比例する（下記「計測結果」）。1000 万チャンク（10 万列 × 100 行グループ）だと polars で約 5 秒・約 6GB の見込み | フッタは Load 時に 1 回だけ解析し、グラフ操作のたびに解析し直さない。メタデータ読込に pyarrow は使わない（polars の約 2 倍の時間とメモリ） | 計測済み（1000 万チャンクは外挿） |
| 疎な超ワイド列 | 大半が null の 10 万列。ワイドのままだとフッタが巨大になる | ワイドのままを優先する。フッタが遅ければ、まずワイドのまま行グループを減らすか列方向に分割する。ロング形式（行 id, 列名, 値）は最後の手段。理由：列ごとの型（int / float / 日付 / カテゴリとその辞書）がスキーマから消え、値の列を型ごとに分けたり別の型カタログで管理したりする必要が出るため。加えて、x と y を揃えるのに行 id での結合が要る | 方針は決定、閾値は要計測 |
| メモリ 16GB | 密な float64 なら 6 列 × 1 億行で約 5GB。集約の中間データも乗る | 使う列だけ読む。null を除いて読む。float32 化を検討 | 要計測 |
| 点描画 | 100 パネル × 平均 100 万点はどの描画系でも描けない | サーバー側でビン集約して画像化 | 確実 |
| ホバー | ラスタ化で点単位のホバーが消える | クリック位置の近傍点をサーバーに問い合わせる | 設計判断 |
| 箱ひげの外れ値 | 1.5IQR の外が数百万点になり得る | 上限で間引く、または外れ値も密度表示 | 確実 |
| 平滑化 | 1 億点に直接は適用できない（lowess は論外）。スプラインは x の狭義単調増加を要求する見込み | x をビン集約してから適合する。並列化前提 | 単調性要件は要確認 |
| 依存の重さ | datashader は numba/dask 依存で PyInstaller 化が壊れやすい。statsmodels も重い | polars + numpy で自作。lowess は自前実装も可 | 推測 |
| 列リスト UI | 10 万列をそのまま一覧に出すと破綻する | サーバー側検索＋上位 N 件、または仮想スクロール | 確実 |
| オフライン | CDN 参照は動かない | JS/CSS を全て同梱する | 確実 |
| Windows Server 2016 | WebView2 が入っていない前提。Python・Qt6 の動作も未確認 | WebView2 固定版ランタイムの同梱（約 150MB 増）、ブラウザ起動、または Qt 案。実機で起動確認する | 要確認 |
| CPU | polars の標準ビルドは AVX2 対応 CPU が前提。対象 PC の CPU は限定できない（任意の環境で動かす） | AVX2 非対応でも動く構成にする（互換ビルドを使う、または起動時に判定して切り替える）。方法と速度差は要調査 | 前提は確定、方法は要調査 |

## 計測結果

### フッタ読込（2026-10-26）

合成した疎な超ワイド Parquet で、列数（1 千〜10 万）と行グループ数（1〜100）を変えて計測した。

- 条件：1 行グループは 100 行、先頭 6 列が密、残りは 1% だけ値がある（うち 5% はカテゴリ列）、統計値あり。
- 環境：Ryzen 5 7600X3D、ローカル SSD、OS のファイルキャッシュが効いた状態。
- RSS はプロセス全体の値で、インタプリタ分の約 50MB を含む。
- スクリプトは `tmp/footer_bench.py`（作業後に削除）。

| 列数 | 行グループ数 | 列チャンク数 | フッタ (MiB) | pyarrow `read_metadata` (s / MiB) | polars `collect_schema` (s / MiB) | polars 6 列射影 (s / MiB) |
| --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 1 | 1 千 | 0.2 | 0.004 / 47 | 0.003 / 50 | 0.005 / 48 |
| 1,000 | 10 | 1 万 | 1.1 | 0.012 / 44 | 0.007 / 59 | 0.010 / 59 |
| 10,000 | 1 | 1 万 | 1.9 | 0.037 / 46 | 0.019 / 51 | 0.021 / 56 |
| 1,000 | 100 | 10 万 | 10.9 | 0.10 / 112 | 0.040 / 103 | 0.044 / 130 |
| 10,000 | 10 | 10 万 | 11.6 | 0.12 / 153 | 0.047 / 114 | 0.050 / 121 |
| 100,000 | 1 | 10 万 | 18.7 | 0.43 / 306 | 0.19 / 275 | 0.17 / 286 |
| 10,000 | 100 | 100 万 | 109 | 0.97 / 974 | 0.32 / 560 | 0.33 / 584 |
| 100,000 | 10 | 100 万 | 116 | 1.24 / 1148 | 0.50 / 644 | 0.47 / 674 |
| 100,000 | 100 | 1000 万 | — | — | — | — |

わかったこと：

- 時間・メモリともに、列チャンク数（列数 × 行グループ数）にほぼ比例する。列数と行グループ数のどちらで増えても差は小さい。
- フッタは 1 チャンクあたり約 120 バイト。
- polars は 100 万チャンクあたり約 0.5 秒・約 600MB。pyarrow はその約 2〜2.5 倍の時間と約 2 倍のメモリを使う。
- 6 列の射影読込は `collect_schema` とほぼ同じ時間で、フッタ解析が支配的。
- 1000 万チャンクのファイルは、pyarrow の writer が RSS 4GB の上限を超えたため生成を打ち切った。比例で外挿すると、polars で約 5 秒・約 6GB、pyarrow で約 12 秒・約 11GB。
- writer 側も 100 万チャンクで約 2GB を使う。外部ツールが 1000 万チャンクのファイルを書くこと自体が重いので、実データでは行グループが少ない可能性が高い（未確認）。

### 繰り返し scan の時間とメモリ（2026-10-26）

10 万列 × 10 行グループ（100 万チャンク、フッタ 116MiB）のファイルを、1 プロセス内で 20 回、および 200 回繰り返し読んだ。RSS は各回の直後の値、peak は Windows の peak working set。スクリプトは `tmp/repeat_scan_bench.py`（作業後に削除）。

| 読み方 | 2 回目以降の 1 回の時間 | RSS（20 回 → 200 回） | peak（200 回） |
| --- | --- | --- | --- |
| A：毎回 `scan_parquet` → `collect_schema` | 0.42〜0.88 秒（初回と同じ） | 1 回目の直後 534MiB、以後 550〜630MiB | 750MiB（20 回） |
| B：毎回 `scan_parquet` → 6 列 `collect` | 0.41〜0.53 秒（初回と同じ） | 670〜790MiB → 750〜850MiB | 961MiB |
| C：`scan_parquet` は 1 回、同じ LazyFrame から 6 列 `collect` を繰り返す | 0.04 秒（初回 0.46 秒） | 650〜780MiB → 760〜890MiB | 913MiB |

わかったこと：

- `scan_parquet` を呼び直すと、そのたびにフッタを解析し直す。同じ LazyFrame を使い回せば、解析は初回だけで済む（約 10 倍速い）。
- フッタ解析後に何も参照していなくても（A）、RSS は解放されず約 600MiB のまま残る。プロセスは一度使ったメモリを OS に返さないと考えて設計する。
- 繰り返しで RSS と peak は少しずつ増えるが、200 回では 1 回分の約 1.4 倍で頭打ちになった。際限なく増えるリークではない。
- 1000 万チャンクに比例で外挿すると、解析後に約 6GB を掴み続け、繰り返しで約 9GB まで増える見込み。16GB の PC では、このメモリを UI と同じプロセスに抱えると重い。
