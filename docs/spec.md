# ddviz 仕様

列をドラッグ＆ドロップしてグラフを組み立てる可視化アプリ。オフラインで動くスタンドアローン exe として提供する。

## 要件

| 項目 | 内容 |
| --- | --- |
| 実行形態 | exe 単体。オフライン環境で動作する。exe 1 ファイルでなくてもよく、フォルダ（zip）で配布してよい（2026-10-26 ユーザー回答） |
| 対象 OS | Windows 11、Windows Server 2016 |
| Server 2016 の環境 | Edge・WebView2 Runtime は入っておらず、追加のインストールもできない。必要なものはすべて ddviz に同梱する。RDP で複数のユーザーが同時にログインする共有サーバーとして使われる。延長サポートが終わる 2027-01 以降も、当面ずっと対応する（いずれも 2026-10-26 ユーザー回答） |
| メモリ | 16GB RAM の PC で問題なく動くこと |
| 入力 | Parquet ファイル、または Parquet を格納したフォルダを指定して Load する |
| データ置き場 | ローカル SSD。ネットワークドライブは想定しない |
| グラフ種別 | 散布図、箱ひげ図（他種別は後回し） |
| フィルタ | 読み込んだデータのローカルフィルタ |
| D&D で指定する役割 | x/y 軸、facet（col, row）、第 n x/y 軸、overlay（≒symbol）、color |
| 散布図の平滑線 | csaps、GCV 平滑化スプライン、lowess から選択（必須） |
| インタラクティブ性 | いずれも必須（2026-10-26 ユーザー回答）。下の表を参照 |

| 操作 | 内容 |
| --- | --- |
| ホバー | マウスオーバーで、カーソルの下の行の値（行単位）を即座に表示する。ビン単位の情報（件数など）では足りない |
| ズーム・パン | 拡大・移動できる |
| 凡例クリック | 系列のアクティブ・非アクティブを切り替える。非アクティブは完全な非表示ではなく、透明度を下げて表示する |
| 凡例の右クリック | クリックした系列だけをアクティブにし、残りを非アクティブにする。もう一度右クリックすると、すべての系列をアクティブに戻す |
| 範囲選択 | 選んだ行をハイライトし、選んだ行を表で表示する |
| 描画領域の大きさ | グラフの描画領域を自由に大きくできる（2026-10-27 ユーザー要望）。窓の大きさに追従し、欄を畳んだり境界をドラッグしたりして広げられる。パネルが多くても 1 パネルを読める大きさに保つ。方式は「インタラクションの設計案」の「描画領域の大きさ」 |

## データの性質

- 規模：1 億行 × 10 万列、facet は 10 × 10 程度。
- 10 万列はかなり疎（大半が null）。
- 列の型は数値中心で、カテゴリが混在する。
- 1 つのグラフで使うのは数列だけ。全列を描画に使う用途はない。
- 全量ロードはしない。グラフに必要な列だけを読む。
- Parquet は ddviz の外で作られ、渡されたものを読む。行グループのサイズやファイルの分け方は ddviz 側で選べない前提で設計する。
- 必要なら、読み込み時に ddviz が裏で変換やキャッシュ作成（フッタの索引化、列方向の分割など）をしてもよい。ただし、ユーザーに追加の作業（変換コマンドの実行、設定、待ち時間の明示的な操作など）をさせる UX は不可。変換は Load の中で自動で行う。

## 技術スタック

UI は htmx 案に決めた（2026-10-26 ユーザー判断）。描画には plotly.js を同梱し、WebView2 の固定版ランタイムを同梱して pywebview で窓を開く。理由は「Server 2016 と使い捨てプロセスの観点での比較」。以下は検討した 3 案。

| 案 | 使う言語 | 長所 | 短所 |
| --- | --- | --- | --- |
| FastAPI + htmx + 少量 JS | 周辺 UI（ファイル選択、列リスト、フィルタパネル）は htmx、D&D と描画は JS（SortableJS など）、データ処理は Python | ビルド工程なし。グラフ仕様をサーバー側で保持でき、フロントの状態管理がほぼ不要 | htmx 単体では D&D と描画はできない。描画まわりの JS が増えると htmx との二重管理が窮屈になる。Server 2016 では WebView2 の扱いが SPA 案と同じく要る |
| Svelte・Vue の SPA + Python サーバー | 画面は JS（Svelte か Vue）、データ処理は Python | 状態管理がきれい | Node のビルドが増える（実行時は不要）。Server 2016 では WebView2 も Edge も無く、インストールもできないため、固定版ランタイムの同梱が要る |
| PySide6 + pyqtgraph | すべて Python（QtWebEngine を使わない限り JS なし） | ネイティブ窓で WebView2 が不要 | この規模では点を直接描けないため、高速描画の利点が効きにくい |

JS を書かずに済むこと自体は選定基準にしない。Python と JS は適材適所で使い分ける。

最初の検討での評価：

- 当初の推奨は「htmx 案で始め、JS が膨らんだら SPA 案へ移る」。
- 1 億行 × 10 万列の規模では、フロントは集約済み画像と軸を表示するだけになるため、htmx 案はむしろ成立しやすい。
- PySide6 案の売りだった大量点の高速描画はこの規模では効かず、優位はほぼ消える。

UI に送るデータの量は、データの行数ではなく画面の大きさで上限を決める（2026-10-26 決定）。集約はすべて Python 側で行う。1 億行の点はどの案でも送れないため、散布図は集約済みの画像の層と軸として送る。点の形式そのものを禁じるわけではない。ただし今は、ズームしても「画像の層 + 代表行」の 1 通りで描く。理由：点のモードを足すと、ズームで描き方が切り替わり、見た目もホバー・範囲選択・凡例の処理も 2 通り要るため。代表行のホバーは、カーソルから 1 ピクセル以内の点を返すので、plotly の SVG 版と精度は変わらない。overlay（≒ symbol）は、点がまばらなときに子プロセスで記号の形を描いて対応する。見た目が足りなければ、表示範囲の点が一定数以下のときに点を送るモードを検討する。

#### Server 2016 と使い捨てプロセスの観点での比較（2026-10-26）

確認した事実：

- Qt 6 の公式の対応 OS は Windows 10 1809 以降（Qt 6.5〜6.7 の Supported Platforms）。Server 2016 は 1607（build 14393）相当なので対象外。動くかは実機で確認する。
- WebView2 の対応 OS は Edge と同じで、Server 2016 を含む。Server 2012 では、OS のサポート終了とともに Edge・WebView2 の更新が止まった（Evergreen 版も固定版も同じ）。止まった後も、最後の版は動き続ける。
- Server 2016 の標準ブラウザは IE11。Edge が入っていないので、「既定のブラウザで開く」方式は使えない。

| 観点 | htmx 案・SPA 案 | PySide6 + pyqtgraph 案 |
| --- | --- | --- |
| Server 2016 での表示 | WebView2 の固定版ランタイムを同梱し、pywebview（pythonnet と .NET Framework 4.6.2 以上が要る）で窓を開く | Qt の DLL を同梱するだけ。ただし 1607 は公式の対象外 |
| RDP の共有サーバー | localhost のポートは、同じ機械の他のユーザーからも見える。ランダムなポートとトークンによる認証が要る。WebView2 のユーザーデータは、各ユーザーの LOCALAPPDATA に置く | ポートを開かないので問題なし |
| 使い捨てプロセスとの連携 | 1 リクエストを 1 タスクにし、サーバーが子プロセスを起動して PNG を受け取る。操作が来たら古い子を kill する。進捗は SSE で送る | QProcess のシグナルで終了と進捗を受け取り、kill する。差は小さい |
| 軸・ズーム・パン | 自前の JS で書く | pyqtgraph の ImageItem と軸、ズームとパンが最初から使える |
| 2027-01 以降 | 固定版ランタイムを、Server 2016 で動く最後の版に固定する | Qt と PySide6 を、Server 2016 で動く版に固定する |

- UI のプロセスは polars を import せず、子プロセスから画像を受け取るだけなので、使い捨てプロセスとの連携のしやすさは、どの案でも大差ない。
- Python も、2027-01 以降の版は Server 2016 を外す可能性がある（PEP 11 は、Microsoft がサポートを終えた OS を外す方針）。どの案でも Python のバージョンは固定する。

Server 2016 の実機も VM も、試す環境は無い（2026-10-26 ユーザー回答）。そのため、Qt 6 が 1607 で動くかを出荷前に確かめられない。

決定：htmx 案（2026-10-26）。描画には plotly.js を同梱し、WebView2 の固定版ランタイムを同梱して pywebview で窓を開く。理由：試す環境が無いなら、Server 2016 を公式にサポートしている WebView2 の経路を選ぶほうが安全なため。Web 案で余分に要るもの（固定版ランタイム、pythonnet、localhost の認証）は、手間は増えるが動作は読める。当初は PySide6 案を推したが、それは実機で確認できることが前提だった。

#### plotly のホバーで選ばれる点（2026-10-26）

plotly.js v4.1.1 で、同じ座標に点を重ねて `Plotly.Fx.hover` を呼び、どの点が選ばれるかを調べた（`tmp/look/hover_test.html`、作業後に削除）。

| トレース | 同じトレース内で重なったとき | トレースをまたいで重なったとき |
| --- | --- | --- |
| scatter（SVG） | index が最大の点 | 後のトレースの点 |
| scattergl | index が最大の点 | 前のトレースの点 |

- 既定は `hovermode: "closest"`、`hoverdistance: 20`（px）。カーソルから 20px 以内で最も近い点を出し、その外なら何も出さない。
- SVG では、カーソルを覆うマーカーは距離がほぼ同じに扱われ、最後に描かれた点、つまり見えている一番上の点が選ばれる。scattergl では、トレースをまたぐと見えている点と一致しないことがある。
- どちらも、重なっている点の件数は出さない。

#### 見た目とコードの比較（2026-10-26）

同じ集約結果（2 × 3 パネル、200 × 200 ビン、log 件数、viridis）を plotly（`go.Heatmap` と `make_subplots`）と pyqtgraph（`ImageItem` と `GraphicsLayoutWidget`）で描いて比べた。スクリプトは `tmp/look_compare.py`（作業後に削除）。

- plotly は、ホバー、ツールバー（ズーム、パン、リセット、PNG 保存）、カラーバー、パネルのタイトルが標準で付く。手を入れなくても整った見た目になる。
- pyqtgraph は、白背景に設定すれば十分読める。ただし、カラーバー、ホバーの表示、凡例は自分で足す必要がある。既定は黒背景で、計測器のような見た目になる。
- PySide6 案では plotly は使えない。plotly は JS のライブラリなので、Qt で使うには QtWebEngine（Chromium を同梱）が要る。QtWebEngine を使うと、配布物は Web 案と同程度に重くなり、しかも Qt 6 が 1607 で動くかというリスクは残る。
- 10 × 10 パネルを plotly の Heatmap で描いたときの描画速度は未計測。重ければ、パネルを PNG にして `layout.images` で貼る。

### プロセス構成

Parquet の読込と集約は、UI とは別のプロセスで行う（2026-10-26 決定）。理由：フッタ解析や読込で使ったメモリを、プロセスは OS に返さない（「計測結果」）。UI のプロセスは集約結果だけを受け取り、小さいまま保つ。

要件：操作していない間にデータ用プロセスがメモリを占有し続けることは許容しない（2026-10-26 ユーザー判断）。常駐ワーカーが LazyFrame を保持すると、100 万チャンクで約 0.9GB、1000 万チャンクで約 9GB を掴み続ける見込みで、これは不可。

前提となるトレードオフ：フッタを解析済みのまま保持すればメモリを占有し、保持しなければ読込のたびに解析時間がかかる。待機プロセスを先に立てておく工夫ではこの関係は変わらない。両方を減らすには、1 回の読込で解析するフッタそのものを小さくするしかない。

候補：

| 案 | 内容 | 占有し続けるメモリ | 1 回の読込の待ち時間 | 課題 |
| --- | --- | --- | --- | --- |
| 1. 列分割キャッシュ（遅延変換）+ 使い捨てプロセス | 元ファイルを列方向に分割したキャッシュ（1 列 = 1 ファイル）を、列を初めて使うときに作る（下記「遅延変換」）。import 済み（フッタ未解析）の待機プロセスを先に立て、読込のたびに必要な列のファイルのフッタだけを解析し、終わったらプロセスごと捨てる | 待機プロセスの約 50MB | 分割済みなら分割後のフッタ解析のみ（約 0.01 秒）。列グループを初めて使うときは、その変換の分だけ待つ | 初回使用時の変換時間とキャッシュのディスク使用量 |
| 2. アイドル終了する常駐ワーカー | 操作中は常駐して LazyFrame を使い回し、一定時間操作がなければ終了してメモリを返す | 操作していない間はゼロ。操作中は案 3 と同じ | 2 回目以降は約 0.04 秒。アイドル後の最初の 1 回は、起動・import・フッタ解析の分だけ待つ | 操作中の占有量は減らない。アイドル判定の時間は未定 |
| 3. 解析済み待機プロセス + 使い捨て | import とフッタ解析まで済ませた待機プロセスを先に立てておき、1 回使ったら捨てて次を立てる | 待機プロセスがフッタ分（常駐ワーカーと同じ）を占有する | 待ちはほぼ隠せる | 占有量は常駐ワーカーと変わらない。入れ替えの間は 2 プロセス分が同時に乗る |
| 4. 常駐ワーカー | 1 つのワーカーが常駐し、ファイルごとに LazyFrame を保持する | フッタ分 + これまでで最大の読込・集約のピーク | 2 回目以降は約 0.04 秒 | 要件を満たさない |
| 5. 素の使い捨てプロセス | 読込のたびにプロセスを起動して終了する | ほぼゼロ | 毎回、起動・import 約 0.7 秒とフッタ解析（100 万チャンクで約 0.5 秒、1000 万チャンクで約 5 秒） | 操作のたびに 1〜6 秒待ち、D&D での試行に合わない |

- 案 1 を採用する（2026-10-26 決定）。案 2 は読込・集約のメモリも掴み続けるため、要件に合わない（下記）。
- 使い捨てプロセスが終了すれば、そのプロセスが使ったメモリ（フッタ分も、読込・集約で膨らんだ分も）はすべて OS に返る。メモリを占有し続けるのは、待機プロセスの約 50MB と UI のプロセスだけになる。

#### 遅延変換

実データの容量は不明（2026-10-26 ユーザー回答）。1 億行 × 10 万列 = 1 兆セルのため、容量は充填率しだいで数 GB〜数百 GB と 100 倍の幅がある（充填率 0.01% で約 8GB、1% で約 800GB）。そこで、容量に比例する処理を Load 時に行わない。

- Load 時はフッタ解析とスキーマ取得だけを行う（100 万チャンクで約 0.5 秒）。
- グラフで列を初めて使ったとき、その列だけを分割キャッシュに書き出す。2 回目以降は分割後のファイルを使い捨てプロセスで読む（約 0.01 秒）。
- 実装（2026-10-26 試作）：UI のサーバーが、グラフで使う列のうちキャッシュに無いものを調べ、あれば集約の前に変換のタスク（`convert`）を 1 つ worker に渡す。worker は元ファイルを 1 回だけ `scan_parquet` し（フッタの解析は 1 回）、列ごとに `select(列).sink_parquet` で一時名に書いてから rename する。集約は、列ごとのファイルを横に連結して読む（`src/ddviz/scan.py`、`cache.py`、`convert.py`）。

列グループの大きさ・置き場所・破棄条件（2026-10-26 決定。計測は「遅延変換の試作」）：

| 観点 | 決定 | 理由 |
| --- | --- | --- |
| 列グループの大きさ | 1 列 = 1 ファイル。ファイル名は列の位置（`c000123.parquet`） | 変換の時間もピークメモリも、1 ファイルに入れる列数に比例以上に増える。polars は行グループを、疎な列も null を含む全幅でデコードし、複数の行グループを並列に先読みするため。1 千万行で、100 列を 1 ファイルにするとピーク約 5.4GB、1 列なら約 0.3GB。行グループの大きさは ddviz では選べないので、メモリを抑えるには 1 回に書く列を減らすしかない。ファイル数は、これまでに使った列の数だけになり、10 万列すべてにはならない。初回の待ちの固定分（元ファイルのフッタ解析）は、1 回のグラフで使う列をまとめて 1 タスクで変換すれば 1 回で済む。列名には、ファイル名に使えない文字が入りうる |
| 置き場所 | `%LOCALAPPDATA%\ddviz\cache\columns\<元ファイルのパスのハッシュ>\`（ユーザーごと）。アプリを閉じても残す（2026-10-26 ユーザー判断） | 必ず書き込めて、設定も要らない。データのフォルダは書き込めるとは限らない。共有サーバーでは同じデータでもユーザーごとに別のキャッシュになるが、同時に使うのは 1 人なので競合はしない |
| 元ファイルが変わったとき | Load 時に、元ファイルのサイズと更新日時（`st_mtime_ns`）を `source.json` と比べ、違えばその元ファイルのキャッシュをすべて消す | 古い列と新しい列が混ざると、行が揃わない |
| 容量の上限 | 固定の上限（既定 10GB）。超えたら、最後に使った日時が古い列から消す。上限は `config/settings.toml` の `cache.max_gb` から読む。既定値も含めて 2026-10-26 ユーザー判断 | 1 億行の密な数値列は 1 列で約 730MB、疎な列（1% 充填）は約 10MB。今のグラフで使う列は消さない |
| 期限 | N 日使わなかった列を消す。N は `config/settings.toml` の `cache.max_unused_days` から読み、既定は 30（2026-10-26 ユーザー判断） | 元ファイルが消えたり移動したりした分も、いずれ消える |
| 最後に使った日時 | 列のファイルの更新日時。集約が終わったら `os.utime` で今にする | 別の索引ファイルを持たずに済む。NTFS の最終アクセス日時は、既定で更新されないことがある |
| 破棄する時機 | Load 時（期限と容量）と、変換の後（容量） | どちらも、キャッシュのファイルを開いている worker が無いとき。Windows では開いているファイルは消せない（消せなければ飛ばす） |
| 変換の途中で落ちたとき | 書きかけは一時名（`.tmp`）のまま残る。次に Load したときに消す | rename の後のファイルだけを完成品として扱う |
| 設定ファイル | exe と同じフォルダの `config/settings.toml`。開発環境ではリポジトリの `config/settings.toml`。無い項目は既定値を使う | ユーザーに設定の作業はさせない（「データの性質」）。既定値で動き、管理者が変えたいときだけ書き換える |

- 初回の待ちは「元ファイルのフッタ解析（100 万チャンクで約 0.5 秒、1000 万チャンクで約 5 秒の見込み）+ 1 列あたり約 0.45 秒（1 億行の密な列）」。疎な列は 1 千万行で 1 列 0.02 秒ほどなので、1 億行でも 1 列 0.2 秒程度の見込み（未計測）。
- 集約を元ファイルではなく列ごとのファイルの連結から読んでも、1 億行で遅くならず、ピークはむしろ減った（3.9GB → 2.7GB）。
- 入力がフォルダ（複数の Parquet）のときのキャッシュは未実装。試作は 1 ファイルだけを受ける。
- どの案でも、読込中のピークメモリは減らない。6 列 × 1 億行のビン集約で約 3.8GB（「計測結果」）。
- 読込・集約で膨らんだメモリも OS に返らない。そのため案 2 は、操作中もフッタ分に加えて集約のピーク（約 4GB）を掴み続ける。案 1 のように 1 回ごとにプロセスを捨てる構成のほうが要件に合う。
- polars の import 時間は、`uv run` の開発環境で 5 回計測し、いずれも約 0.72 秒だった（何もしないプロセスの起動は約 0.055 秒）。exe 化した後の値は未計測。
- 変換中は、グラフの編集（D&D、フィルタ、ズームなど）を受け付けず、進捗だけを表示する（2026-10-26 ユーザー判断）。そのため、変換の途中で次の操作が来ることはなく、変換を kill するかどうかを決める必要がない。中止ボタンを置くかは未定。

実装は `src/ddviz` にある（`runner.py`、`jobs.py`、`worker.py`、`task.py`、`server.py`）。タスクの種類は `schema`（Load）、`convert`（遅延変換）、`plot`（集約と画像化）。変換中に来た描画の要求は 409 で断る。描画のタスクを渡すと走っている子を kill するため、変換を守る（画面は変換中の編集を受け付けないので、通常は来ない）。

### インタラクションの設計案（未確定）

前提：UI に送る量を画面の大きさで上限する（「技術スタック」）、データ用のプロセスを常駐させない（「プロセス構成」）。この 2 つを守ったまま、必須の操作（「要件」）を実現する。

plotly との分担：plotly.js はそのまま埋め込み、軸、ズーム・パン、凡例、範囲選択の操作に使う。画像の層は plotly のトレースにせず、画面が plotly の軸から位置を求めて自前の canvas に描く（下記「画像の層」）。plotly 自身はどの行がカーソルの下にあるかを知らないので、ホバーで出す行は UI のサーバーが引き、表示は plotly の挙動（下記）に合わせる。

- 画像の層（2026-10-28 決定。比較と計測は「画像の層の持ち方の比較」）：
  - 系列の画像は、plotly の 2 枚の SVG（軸と格子の層、凡例・ズームの枠・選択の枠の層）の間に置いた 1 枚の canvas に、画面が描く（`static/js/layers.js`）。パネルの位置と範囲は plotly の軸（`_offset`、`_length`、`l2p`）から求め、パネルの枠で切り抜く。canvas はポインターのイベントを受けない。
  - plotly の図には、凡例の項目を持つ空の scatter（系列ごとに 1 本、`legendgroup` は `s<系列>`）と、軸を残すための空の scatter（パネルごとに 1 本）だけを置く。10 × 10 パネル × 5 系列で 105 本。
  - 軸が変わるたびに描き直す（`plotly_relayouting`、`plotly_relayout`、`plotly_afterplot`、`plotly_restyle`）。パンのドラッグ中も `plotly_relayouting` が動きごとに来て、軸の `range` と `l2p` はその時点の値になっている（2026-10-28 確認）。1 回の描き直しは 10 × 10 パネル × 5 系列で 2〜3ms。画面の拡大率（`devicePixelRatio`）が変わったときも描き直す（窓を別のモニターに動かしたときなど。plotly はイベントを出さない）。
  - 結果を差し替えるとき、図が今の図と軸の範囲以外で同じなら（同じグラフで同じ大きさ。ズーム・パンの結果や全体図に戻すときがそう）、plotly は呼ばずに canvas だけを描き替え、範囲が違えば範囲だけを `Plotly.relayout` で変える。理由：`Plotly.react` は、トレースが空でも 100 パネルの軸を描き直すのに約 0.4 秒かかる。
  - 範囲選択のハイライトの層も、同じ canvas の系列の上に描く。

用語：この節の「ビン」は、散布図のプロット領域の 1 ピクセル（またはそれに近い大きさ）のマス目を指す。ヒストグラムを描くわけではない。点が 1 つ以上あるピクセルを、系列の色で塗った画像として散布図を送る。点として描いた散布図とほぼ同じ見た目になる（`tmp/scatter_compare.py` で、100 万点の scattergl と並べて確認した。作業後に削除）。

- ホバー（行単位）：
  - 集約のとき、使い捨てプロセスが空でないビン（パネル × 色 × bin_x × bin_y）ごとに代表行を 1 つ選ぶ（行番号が最大の行）。
  - 代表行の行番号とホバーに出す列の値を、タスクのディレクトリに npy で書き出す。加えて、ピクセルごとにどの系列の点があるかのビットマスク（`occupancy.npy`、形はパネル × 高さ × 幅）を書く。20px 以内の最近傍を、全系列のキーを引かずに探すため。
  - UI のサーバーはこれを memmap で開き、ホバーのたびにビンの位置から引く。プロセスの起動も Parquet の読込も無いので、即座に返せる。
  - 代表行の決め方は、plotly の scatter（SVG）に合わせ、「見えている一番上の点」とする。カーソルのピクセルに点があれば、そこにある系列のうち一番上に描かれている層（非アクティブの層は奥に回るので、アクティブな層が優先される）を選び、その系列の中で行番号が最大の行を出す。ピクセルが空なら、20px 以内で最も近い、点のあるピクセルを使う。20px 以内に無ければ何も出さない。
  - 加えて、そのピクセルにある行数を出す（plotly には無い、ddviz の拡張）。
  - 集約では、空でないビン（パネル × 系列 × bin_x × bin_y）ごとに、行番号の最大値と件数を求める。どの層が一番上かは表示のときに決まるので、系列ごとに持っておく。
  - ホバーに出す列（x、y、color、facet と、ユーザーが選ぶラベル列）を変えたら、集約し直す。
  - 実装（2026-10-26 試作、`src/ddviz/hover.py`、`static/js/hover.js`）：画面は mousemove でカーソルの下のパネルを決め、plotly の軸（`_offset`、`_length`、`p2l`）でカーソルをビンの座標に直して、UI のサーバーに問い合わせる。ズームして 1 ビンが複数の画素になっても 20px を画面の画素で数えるよう、1 ビンあたりの画素数も送る。層の順（アクティブな系列を後ろから、続いて非アクティブな系列を後ろから）は、凡例の状態から画面が決めて送る。問い合わせは同時に 1 つだけにし、待つ間の mousemove は最新の 1 つにまとめる。plotly の hover は切り（`hovermode: false`）、ラベルは系列の色の枠で自前で描く。
  - 文字列の列は、ホバー用に辞書の番号（int32）と辞書（manifest）に分けて書く。
- ズーム・パン（2026-10-27 決定。比較と計測は「ズーム・パンの方式の比較」）：
  - 表示範囲が変わるたびに、使い捨てプロセスで表示範囲だけを集約し直す（下の案 A）。1 ビンは画面の 1 画素のまま。
  - 結果が来るまでは、plotly が今の画像を新しい軸に合わせて引き伸ばして表示する。パンで新しく見えてくる帯は、結果が来るまで空白のままにする（2026-10-27 ユーザー判断）。
  - 待っている間は、引き伸ばした画像を半透明（不透明度 0.35）にし、プロットの上に「集約中…」を出す（2026-10-28 ユーザー了承）。理由：前の画像の右端や上端は前の表示範囲の端で、データの縁ではない。完成した絵と見分けがつかないと、差し替えで形が変わったときに、パンが別の位置で確定したように見える（ユーザーの操作の録画で確認）。
  - 最初の集約（データ全体の範囲。以下「全体図」）の結果は、別のグラフを描くまで消さずに持つ。ダブルクリックやモードバーの自動範囲で全体に戻すときは、それを即座に描き直し、集約しない（2026-10-27 ユーザー判断）。ディスクは数十 MB、UI のサーバーのメモリは memmap だけ。
  - 表示範囲の集約は、全体図の水準（color、row、col）とグラフの大きさを使い回す。levels の段（約 0.8〜1 秒）を飛ばし、パネルと系列の並びや色も全体図と同じに保つ。範囲の外の行は集約から除く（`PlotSpec` の `x_range`、`y_range`、`levels`）。
  - 全パネルの x 軸と y 軸は `matches` で揃っているので、表示範囲は 1 つ（最初のパネルの軸の範囲）。
  - plotly のモードバーは、Zoom、Pan、Box Select、Reset axes の 4 つだけを出し、ドラッグの初期は Pan にする（2026-10-28 ユーザー判断）。Reset axes で全体図の範囲に戻ると、全体図を集約せずに描き直す。
  - 画面は `plotly_relayout` で範囲の変化を受け、`POST /api/view` に範囲を送る。新しい要求は走っている集約の子を kill する。古い要求への応答は捨てる。画像を差し替えている最中（約 0.5 秒）に来た `plotly_relayout` も無視しない。最初の実装は無視していたので、その間に離したパンが失われ、軸と画像の範囲が食い違うおそれがあった（2026-10-27 修正）。ドラッグ中に前の要求の結果が届いたら、離すまで差し替えない。結果は canvas の画像だけを差し替え（「画像の層」）、軸は利用者が動かした範囲のままにする。凡例の状態（非アクティブの系列）は差し替えの前後で引き継ぐ。
  - ホバーは、画面に描いている結果（全体図か表示範囲か）のタスク番号で引く。UI のサーバーは全体図と最新の表示範囲の 2 つの結果を開いておく。
  - plotly は、トレースが 1 つも無いサブプロットの軸を描かない。表示範囲に行の無いパネルが軸ごと消えたので、空の scatter トレースを置く（2026-10-27 確認）。画像を canvas に移してからは、すべてのパネルに置く。
- 描画領域の大きさ（2026-10-28 決定。計測は「描画領域の大きさを変えたときの集約」）：
  - 図は描画領域（`#stage`。窓から操作欄などを除いた残り）の大きさで集約する。1 ビンは画面の 1 画素のまま。
  - 大きさが変わったら、変化が止まってから 300ms 後に 1 回だけ、いま見えているもの（全体図か表示範囲）をその大きさで集約し直す。画面は `ResizeObserver` で描画領域の大きさを見る。窓のリサイズにも境界のドラッグにも「終わった」というイベントは無いので、止まるのを待つ。フィルタ欄の開け閉めや幅の変更も、同じ仕組みで追従する。
  - 待っている間は、ズーム・パンと同じく、今の画像を半透明にして「集約中…」を出す。大きさの変化が止まったとき、窓に収まる図は `Plotly.relayout` で新しい大きさに引き伸ばし、スクロールする図（下記）は大きさを変えない。
  - 全体図の作り直しは、全体図の水準と、余白を付けたデータの範囲を使い回す（`POST /api/overview`）。余白付きの範囲はすべての行を含むので、結果は全体図と同じで、levels の段（0.6〜1.0 秒）を飛ばせる。表示範囲は、範囲を保ったまま新しい大きさで集約し直す（`POST /api/view` に大きさも送る）。
  - ズーム中に大きさが変わったときは、表示範囲だけを作り直し、全体図は古い大きさのまま持っておく。全体に戻ったときに、古い全体図を引き伸ばして即座に描き、新しい大きさで集約し直す。理由：子は同時に 1 つしか走らず（新しいタスクは前のタスクを kill する）、両方を作ると待ちが倍になる。全体に戻らないこともある。
  - 新しい大きさでもパネルの配置（`GridLayout`）と範囲が今の結果と同じなら、UI のサーバーは子を起動せずに今の結果を返し、走っている別の大きさの集約は止める。画面も描き直さない。スクロールする図は、縦横とも最小の大きさのパネルなら、窓を少し動かしても配置が変わらない。
  - 別のグラフの集約が始まったら、古いグラフの表示範囲や全体図の作り直しの結果は捨てる（UI のサーバーの `plot_id`）。
- パネルが多いとき（2026-10-28 ユーザー判断）：
  - 1 パネルの描画域の最小を 160 × 120 px とする。描画領域に収めると最小を下回るときだけ、図をその大きさで描き、描画領域を縦横にスクロールする。収まるときは今までどおり描画領域いっぱいに描く。
  - スクロールする図では、どのパネルにも目盛りのラベルと、目盛りの上に「g1 = a / g2 = b」の見出しを付ける。外側のパネルだけに付けると、スクロールしたときに読めないため。パネルの間隔は横 50px、縦 44px にする。外側の facet ラベル（上と右）は出さない。
  - スクロールする図は、描画領域の両方向にスクロールバーの幅（17px）を空けて配置を決める。描画領域はスクロールする図のときだけスクロールを許す。理由：大きさの変更中は前の（大きい）図が残るため、収まる図でもスクロールバーが出たまま残った。
  - 比べた案：横は収めて縦だけスクロール（列が多いと幅は狭いまま）、窓に収めて 1 パネルを拡大（拡大のたびに集約が走る）、収めるだけ（10 × 10 で 1 パネル約 94 × 75 px）。
  - 10 × 10 パネルを 1200 × 900 の描画領域に描くと、図は 2250 × 1686 px、空でないビンは 39 万 → 92 万になり、集約は約 0.3 秒、ピークは約 0.5GB 増える。
  - スクロールする図では、凡例（図の右端）と軸の名前（図の左と下）もスクロールで見えなくなる。凡例は HTML にし、軸の名前は図の周りのドロップ先が兼ね、どちらもスクロールの外に置く（「D&D の画面の配置」）。
- D&D の画面の配置（2026-10-28 ユーザー判断。静的な試作で 3 案を切り替えて比べた。試作は作業後に削除）：
  - ドロップ先を図の周りに置く。上が Group X（col）、左が Y、右が Group Y（row）、下が X。図の右の欄に Color と Overlay のドロップ先、その下に凡例を置く。左端の欄は列リスト。
  - ドロップ先は描画領域（スクロールする範囲）の外に置き、軸の名前と facet の列の名前を兼ねる。理由：パネルが多くて図がスクロールしても、どの列を描いているかが見える（「パネルが多いとき」）。plotly の軸の名前は出さない。
  - 凡例は plotly の外の HTML にし、右の欄に置く（スクロールの外）。クリックと右クリックの動きは今と同じ（下記「凡例」）。理由は軸の名前と同じ。
  - 置く：列リストの列をドロップ先に落とす。埋まっていれば置き換える。
  - 第 n 軸：X と Y は、置いた列（チップ）の上に落とすと置き換え、チップの横の空きに落とすと第 n 軸として足す。描けるようになるまでは、置けるだけで描かない（Overlay も同じ）。
  - 入れ替え：置いた列を別のドロップ先に移す。移し先が埋まっていれば、2 つの役割を入れ替える。
  - 外す：チップの × を押すか、チップを列リストかドロップ先の外に落とす。
  - ドラッグ中は、落とすと何が起きるか（置く、置き換え、入れ替え、第 n 軸として足す、外す）を画面に出す。
  - 列リスト：サーバー側で列名を検索し、一致した件数と上位 N 件（試作は 200 件）を返す。大文字と小文字は区別しない。空白で区切った複数のキーワードは、順不同のすべてを含む列を探す。型（数値、カテゴリ）でも絞れる。各列には型と非 null の割合を出す（列がかなり疎なため）。全列の仮想スクロールはしない。10 万列の検索は、試作の画面の中の素朴な部分一致で 1〜14ms だった。
  - 比べた案：B 図の上にドロップ先を 2 段の棚として並べる（図は一番広いが、軸の名前が図の中になり、スクロールで見えなくなる。ドロップ先が軸から離れる）、C 列リストの隣に役割を縦 1 列の欄にまとめる（読みやすいが、横幅を一番取る）。
- 凡例：色（と overlay）の系列ごとに画像の層を分けて送り、フロントで層ごとの透明度を変える。切り替えのたびの再集約は要らない。
  - 層の重なり順は凡例の順とし、後の系列ほど上に描く。非アクティブの系列はアクティブの系列の奥に回す。
  - 処理は flat-pca の `src/flat_pca/webui/static/js/plot_legend.js` に倣う（`legendgroup` 単位で opacity を切り替える。左クリックは切り替え、右クリックはその系列だけをアクティブにし、もう一度で全部に戻す。ダブルクリックは何もしない）。
  - 凡例の項目は、系列ごとの空の scatter トレースが持つ。クリックではその opacity だけを `restyle` し（plotly は図を描き直さない）、canvas は `plotly_restyle` を受けて、凡例の opacity から系列の透明度と重なり順を決めて描き直す（2026-10-28）。以前は image トレースの opacity と zorder を変えていて、zorder の変更が図全体を描き直すので遅かった（「ホバーの試作」「画像の層の持ち方の比較」）。
  - PNG は 1 行目を一番下のビンにして書き、canvas には上下を反転して描く。以前の image トレースで決めた向きをそのまま使っている。image トレースをやめたので、y 軸の反転や `scaleanchor` を打ち消す設定は要らなくなった。
- 範囲選択：
  - 選択は、行番号の一覧ではなく条件（パネル、x と y の範囲、フィルタ）として持つ。
  - ハイライトは、選択の条件を付けた集約の結果を、別の層として canvas の系列の上に重ねて描く（「画像の層」）。
  - 表は、条件に合う行をページ単位で使い捨てプロセスから取り出す（件数と先頭の N 行）。数百万行が選ばれても、表に送るのは表示中のページだけにする。
- 集約のキー：パネル・系列・bin_x・bin_y を 1 つの int64 にまとめる（「ホバーの代表行を加えた集約」の計測結果）。
- 代表行の値は 2 段階で求める。1 段目の集約で行番号の最大値を求め、2 段目で、その行の値を semi join で取り出す。キーの順に並べて列ごとに npy に書き、UI のサーバーは `searchsorted` で引く。
- 矩形選択の範囲：画像の層だけのパネルでも、`plotly_selected` は `range` を返す（2026-10-26 確認）。キーは軸の id で、例えば `{"x12": [x0, x1], "y12": [y0, y1]}`。選ばれた点は 0 件。凡例用の scatter トレースがあるので、モードバーに矩形選択のボタンも出る。

平滑化ライブラリ候補：

- GCV：`scipy.interpolate.make_smoothing_spline`（`lam=None`）
- csaps：`csaps` パッケージ
- lowess：`statsmodels` または自前実装

### ローカルフィルタの設計案（未確定）

要件の「読み込んだデータのローカルフィルタ」は、次のものを指す（2026-10-26 ユーザー回答）。グラフごとに列を選び、数値の列は範囲（スライダー）、カテゴリの列は水準の選択で行を絞り、グラフがすぐに追従する。

配置（2026-10-26 ユーザー判断）：

- フィルタ欄はグラフの左に置き、畳めるようにする。畳むと細い帯になり、掛かっている条件の要約（例：「g1: 3/10、x: −2〜5」）を出し続ける。
  - 理由：グラフの変化を見ながら条件を動かせることがローカルフィルタの価値で、グラフに重なるポップアップでは変化が隠れる。また、閉じていると絞り込み中であることを忘れ、グラフを読み違えるおそれがある。
- フィルタ欄の開け閉めや幅の変更で描画領域の幅が変わると、ビンの数が変わるので集約し直しになる。幅の変更はドラッグを終えたときに 1 回だけ集約し、それまでは今の画像を引き伸ばして表示する（「インタラクションの設計案」の「描画領域の大きさ」で実装済み。描画領域の大きさの変化として扱う）。
- グラフビルダーの列リストも左に要る。フィルタ欄は列リストの下に積む（2026-10-28 ユーザー判断。タブで切り替える案と試作で比べた）。理由：列リストとフィルタ欄を同時に見られ、列をフィルタ欄に直接ドラッグして足せる。タブにすると、掛かっている条件がタブの見出しにしか出ない。フィルタ欄を畳むと、見出しの帯（条件の要約）だけを残し、列リストが縦に伸びる。

未確定の設計：

- 条件の持ち方：グラフ仕様の一部として、列ごとに「数値は範囲、カテゴリは選んだ水準」を持つ（範囲選択と同じく、行番号の一覧ではなく条件として持つ）。
- worker での掛け方：集約の scan に行のフィルタとして掛ける。ホバーの代表行も、範囲選択の表も、同じ条件で絞った行から選ばれる。
- フィルタに使う列も、初めて使うときに遅延変換の対象になる（グラフの列と同じタスクでまとめて変換する）。
- フィルタ欄に出す情報：カテゴリは水準と件数、数値は最小値と最大値。列を 1 つ読むだけの集計（「遅延変換の試作」で 1 列なら軽い）を、フィルタに列を加えたときに worker で行う。
- 追従の速さ：条件を変えるたびに集約し直すので、1 億行では 1 回約 4 秒かかる。スライダーを離したときに集約するか、少し待ってから集約するかなど、いつ集約するかを試作で決める。
- 絞り込みで行が無くなったカテゴリの水準を、凡例やパネルから消すか残すか。消す作りもあるが、色の順が変わって不便なので、残すほうがよいかもしれない（2026-10-26 ユーザー回答。まだ断定しない）。どちらにしても、色は絞り込む前の全水準の並びで割り当てて固定する。そうすれば、ある水準が消えても他の水準の色は変わらない。
- リアルタイムに追従するには、データ全体をメモリに載せ、フィルタは行ごとの状態（除外・非表示）を付け直して描き直す作りが要る。ddviz はデータをメモリに持ち続けない（「プロセス構成」）ので、条件を変えるたびにディスクから読み直す。リアルタイムの追従はあきらめ、スライダーを離したときなどに集約する（2026-10-26 ユーザー了承）。将来速くするなら、水準の少ないカテゴリのフィルタの列を集約のキーに含めておき、チェックの切り替えは画面側で層を組み合わせるだけにする案がある（未検討）。

わかったこと：

- 時間・メモリともに、列チャンク数（列数 × 行グループ数）にほぼ比例する。列数と行グループ数のどちらで増えても差は小さい。

### 繰り返し scan の時間とメモリ（2026-10-26）

10 万列 × 10 行グループ（100 万チャンク、フッタ 116MiB）のファイルを、1 プロセス内で 20 回、および 200 回繰り返し読んだ。RSS は各回の直後の値、peak は Windows の peak working set。スクリプトは `tmp/repeat_scan_bench.py`（作業後に削除）。

| 読み方 | 2 回目以降の 1 回の時間 | RSS（20 回 → 200 回） | peak（200 回） |
| --- | --- | --- | --- |
| A：毎回 `scan_parquet` → `collect_schema` | 0.42〜0.88 秒（初回と同じ） | 1 回目の直後 534MiB、以後 550〜630MiB | 750MiB（20 回） |
| B：毎回 `scan_parquet` → 6 列 `collect` | 0.41〜0.53 秒（初回と同じ） | 670〜790MiB → 750〜850MiB | 961MiB |
| C：`scan_parquet` は 1 回、同じ LazyFrame から 6 列 `collect` を繰り返す | 0.04 秒（初回 0.46 秒） | 650〜780MiB → 760〜890MiB | 913MiB |

わかったこと：

- `scan_parquet` を呼び直すと、そのたびにフッタを解析し直す。同じ LazyFrame を使い回せば、解析は初回だけで済む（約 10 倍速い）。
- フッタ解析後に何も参照していなくても（A）、RSS は解放されず約 600MiB のまま残る。プロセスは一度使ったメモリを OS に返さないと考えて設計する。
- 繰り返しで RSS と peak は少しずつ増えるが、200 回では 1 回分の約 1.4 倍で頭打ちになった。際限なく増えるリークではない。
- 1000 万チャンクに比例で外挿すると、解析後に約 6GB を掴み続け、繰り返しで約 9GB まで増える見込み。16GB の PC では、このメモリを UI と同じプロセスに抱えると重い。

### 列分割キャッシュの変換コスト（2026-10-26）

プロセス構成の案 1 のコストを測った。10 万列 × 10 行グループ（100 万チャンク）のファイルを、polars で 1000 列ずつ 100 ファイルに分割した。分割は `scan_parquet` の LazyFrame を使い回し、`select(1000 列).sink_parquet(...)` を 100 回繰り返す方法で行った。合成条件は「フッタ読込」と同じで、1 行グループの行数だけを変えた。スクリプトは `tmp/convert_bench.py`（作業後に削除）。

| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 1 万 | 290 | 117 | 7.1 | 1,326 | 40 | 0.15 | 0.007 |
| 10,000 | 10 万 | 1,038 | 122 | 16.6 | 2,006 | 204 | 0.23 | 0.008 |

わかったこと：

- 分割後は 1 ファイルのフッタが 0.2MiB 程度になり、使い捨てプロセスでも 6 列を約 0.008 秒で読める（分割前は約 0.5 秒）。
- 変換時間は「固定分 約 5 秒（100 万チャンクのフッタ解析と 100 回の書き出し）+ 元データ 1GB あたり約 13 秒」で近似できる（2 点からの推定）。
- 変換のピーク RSS はデータ量とともに増えた（1.3GB → 2.0GB）。1 億行で頭打ちになるかは未確認。
- 分割後の合計サイズが元より小さいのは、合成データの繰り返しが多いこと、および polars と pyarrow の既定の圧縮方式の違いによる。実データでのディスク使用量の見積もりには使えない。
- 実データのファイルサイズが 100GB なら、ファイル全体の変換には約 20 分かかる計算になる。初回 Load でこれを丸ごと待たせるのは UX 上厳しいため、遅延変換にした（「プロセス構成」）。
- 「1GB あたり約 13 秒」は、この 2 点（行数が少ない）での近似。行数が増えると、変換は圧縮後のバイト数ではなく「行数 × 列数」（null も全幅でデコードする）に比例し、まとめて書く列数を増やすとメモリも膨らむ（「遅延変換の試作」）。

### ズーム・パンの方式の比較（2026-10-27）

ズームとパンで集約し直す方式を、次の 3 案で比べた。再集約が要るのは、集約結果から細かい絵を作り直せないことと、元の値を常駐プロセスに持たない方針（「プロセス構成」）のため。

| 案 | 内容 |
| --- | --- |
| A. 毎回集約し直す | 表示範囲を使い捨てプロセスに渡して集約し直す。結果が来るまでは今の画像を引き伸ばして表示する |
| B. 細かい集約を先に作る | 最初の集約のときに、細かいマス目（画面の k 倍）でも数えてディスクに書いておく。k 倍までのズームは、それを足し合わせて描く |
| C. 周りを含めて集約する | 表示範囲より広め（ここでは 3 × 3 倍）を集約しておき、小さなパンは集約せずに描く |

決定：A（2026-10-27 ユーザー判断）。理由：

- A でも、ズームしてから描き直すまでは 2〜4 秒で、その間は plotly が今の画像を引き伸ばして表示する。B で作れる仮の絵は、これより少し細かいだけ。
- B の細かい集約は、D&D やフィルタで集約し直すたびに作り直すことになり、毎回の集約が遅くなる。k 倍を超えるズームでは結局 A が要る。ホバーの代表行も、細かいマス目ごとに持つと重い（下記）。持たなければ、A の結果が来るまで行を出せない。k = 16 では、そこから描くほうが A より遅い。
- C は小さなパンにしか効かず、ビンが 9 倍になるので、そのコストがズームのたびにかかる。

条件：「遅延変換の試作」と同じ構成の 1 億行（x, y, c が float64、g1, g2 が 10 水準、color が 5 水準の文字列）を、列ごとのファイル（列キャッシュと同じ形）で読んだ。y は x と g1 から作り、ズームで形が見えるようにした。10 × 10 パネル × 5 系列、図 1200 × 900（1 パネル 94 × 75 ビン）。各処理は別プロセスで実行し、プロセスツリー全体の RSS（uv のランチャー配下まで合算）が 9GiB を超えるか、OS の空きメモリが 3GiB を切ったら kill した（計測時の空きメモリは約 11GB）。OS のファイルキャッシュが効いた状態。Ryzen 5 7600X3D、polars 2.1.0。スクリプトは `tmp/zoom/`（作業後に削除）。「倍率」は表示範囲の幅に対する全体の幅の比。

### 画像の層の持ち方の比較（2026-10-28）

「次のアクション」の旧 1 番。画像の層の持ち方を見直し、描画と凡例のクリックを速くするために、exe（WebView2 固定版 156.0.4314.50、Windows 11）で測った。

条件：

- データは「描画領域の大きさを変えたときの集約」と同じ構成の 1 億行を作り直した（x, y, c が float64、g1, g2 が 10 水準、color が 5 水準の文字列。y は x と g1 から作る。100 行グループ）。
- 10 × 10 パネル × 5 系列。窓は既定の 1280 × 860 で、描画領域は 1234 × 692 px。図は 2250 × 1686 px（スクロール。1 パネル 160 × 120）。
- `dist\ddviz\ddviz.exe` を `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=…` で起動し、DevTools のプロトコルで計測の JS をページの中で動かした。
- 時間は `performance.now()` で測り、「a / b」の b は、その後 2 フレーム（`requestAnimationFrame` 2 回）待って描画まで含めた値。各 5〜6 回。exe・worker・WebView2 を合わせたプロセスツリーの RSS と OS の空きメモリを監視した（ピーク約 4.1GB、kill は 0 回）。
- スクリプトは `tmp/`（作業後に削除）。

今の構成（パネル × 系列ごとの image トレース 500 本 + 凡例用 scatter 5 本、図の JSON 416KB）：

わかったこと：

- `newPlot` の時間の大半は、画像ではなく 100 パネルの軸だった。画像を 1 本も持たない図でも 0.40〜0.58 秒かかり、うち `matches`（全パネルの軸を揃える）が約 0.15 秒。`matches` は、1 つのパネルでパンしたときに全パネルを一緒に動かすのに要るので残す。
- ズームの結果への差し替え（`Plotly.react`）も、画像が変わらない全体図への戻りでも約 0.45 秒かかり、大半は軸の描き直し。
- 凡例のクリックで遅いのは zorder の変更（図全体を描き直す）。opacity だけなら 0.07〜0.09 秒。
- パネルごとの合成（F）は、凡例のクリックのたびに合成と `source` の差し替えが要り、速くならない。
- 系列ごとに 1 つの画像トレースで全パネルを覆う形は、image トレースが 1 組の軸にしか属せないので作れない。`layout.images` で図全体に貼る形は、ズーム・パンの間に plotly が画像を軸に合わせて引き伸ばさなくなる。
- パンのドラッグ中は `plotly_relayouting` が動きごとに来て、軸の `range` と `l2p` はその時点の値になっている。canvas は 2〜3ms で描けるので、ドラッグに追従できる。

決定：画像は plotly のトレースにせず、canvas に描く（案 C。2026-10-28 ユーザー判断）。あわせて、系列ごとに全パネルを 1 枚の PNG にまとめ、同じグラフの同じ大きさの結果への差し替えでは plotly を呼ばない。設計は「インタラクションの設計案」の「画像の層」。理由：

- 凡例のクリックが plotly の図の描き直しから切り離され、zorder を使わずに非アクティブの層を奥に回せる。
- 結果の差し替えで軸を描き直さずに済む。
- 範囲選択のハイライトの層を、同じ canvas に重ねるだけで足せる。
- ホバー（hover.js が plotly の軸から位置を引く）、ズーム・パン、リサイズ、範囲選択の操作は、どれも plotly の軸と操作のままで変わらない。
